NDY HUB API Reference

Everything needed to register, authenticate, and connect an app to NDY HUB — NDJOYIT's central identity provider. Every endpoint below is live in production today.

Live in production Updated 2026-08-07 JSON over HTTPS

Authentication model

NDY HUB issues short-lived access tokens (15 minutes, signed JWT) and long-lived refresh tokens (30 days, opaque random string — only its SHA-256 hash is ever stored server-side, so a leaked database row isn't a usable credential).

Any endpoint that issues a session (register confirmation, login, 2FA verify, passkey login, OAuth code exchange, QR-login exchange) returns this shape:

// 200 OK
{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "3f8a...",
  "expiresIn": "15m"
}

Two ways to carry these, pick one:

Client typeHow auth works
Browser (NDY HUB's own web app)The same response also sets two httpOnly cookies — ndyhub_access_token and ndyhub_refresh_token. The app never touches the tokens directly; the browser sends the cookies automatically.
NDYAPPS, mobile, server-to-serverRead accessToken / refreshToken from the JSON body. Send the access token as Authorization: Bearer <accessToken> on every authenticated request.

Endpoints marked 🔒 AUTH require either the cookie or the header. Endpoints marked PUBLIC need neither.

Refresh a session 
POST /auth/refresh
{ "refreshToken": "..." }
Log out 
POST /auth/logout
{ "refreshToken": "..." }

Browser clients can omit the body on both — the cookie carries the token. Refreshing rotates to a brand-new pair and revokes the old refresh token immediately, so a stolen-and-reused refresh token only ever works once. Logout revokes the token and clears both cookies.

Registration

POST /auth/register PUBLIC 5 req/min/IP

Only email and password are required. The rest are the same Passport Card fields exposed later on PATCH /auth/me — sending them here just saves the user a second step.

"email": "person@example.com",      // required
"password": "min 8 characters",    // required
"fullName": "Jane Doe",            // optional, max 100 chars
"bio": "...",                      // optional, max 280 chars
"country": "...",                  // optional, max 56 chars
"website": "https://...",          // optional, valid URL
"linkedinUrl": "https://...",      // optional, valid URL
"instagramUrl": "https://...",     // optional, valid URL
"xUrl": "https://...",             // optional, valid URL
"businessName": "...",             // optional, max 100 chars
"businessRole": "...",             // optional, max 100 chars
"phone": "...",                    // optional, max 32 chars
"bioIsPublic": true,               // optional booleans, all default true
"countryIsPublic": true,
"websiteIsPublic": true,
"socialsIsPublic": true,
"businessIsPublic": true,
"phoneIsPublic": true
Permanent NDY ID: at registration the backend immediately mints a permanent identifier in the form NDY-XXXXXX (e.g. NDY-4F82XK). It never changes and is the user's identifier across every NDY product.

Response — registration does not issue a session directly. The account exists but can't log in until email is confirmed:

{
  "requiresEmailVerification": true,
  "email": "person@example.com",
  "expiresInSeconds": 299
}

expiresInSeconds is always 299 (4 minutes 59 seconds) — the window the just-sent verification email stays valid. Drive a live countdown from it.

Email verification

Verification is link-based, not a code — the email contains a button linking to {WEB_APP_URL}/verify-email?token=.... The link expires in 4 minutes 59 seconds; after that it must be resent.

POST /auth/verify-email/confirm PUBLIC

The token itself is the credential — no session needed to call this.

{ "token": "the-32-char-token-from-the-email-link" }
This is where a brand-new account's first real session is issued — register() no longer issues one directly, so confirming email is what actually logs the user in for the first time. Response is a full session object (see Authentication model).
  • 400 Token is invalid or expired.
  • 409 Token was already used (double-click protection).
POST /auth/verify-email/resend-by-email PUBLIC 5 req/min/IP

Used on the "check your email" screen shown right after registration — no session exists yet to gate a resend behind.

{ "email": "person@example.com" }

Response: { "expiresInSeconds": 299 } — always the same shape whether or not the email is actually registered, so this can't be used to enumerate accounts. Issues a fresh token and a fresh 4:59 window every call.

POST /auth/verify-email/resend 🔒 AUTH

Session-gated equivalent, for a logged-in-but-still-unverified edge case. No body required.

Login

POST /auth/login PUBLIC 5 req/min/IP 
{ "email": "person@example.com", "password": "..." }

Returns one of three shapes depending on account state — a successful request with a different next step, not an error:

CaseResponseWhat to do next
Email not yet verified { "requiresEmailVerification": true, "email": "..." } No expiresInSeconds here — this reports existing state. Call verify-email/resend-by-email for a fresh link.
2FA enabled { "requires2fa": true, "challengeToken": "..." } Continue with POST /auth/2fa/verify.
Success Full session object Store the tokens / rely on the cookie.

Wrong email or password always returns a generic 401 Incorrect email or password. — never reveals which part was wrong. A suspended account returns 401 This account has been suspended.

Password management

POST /auth/change-password 🔒 AUTH 5 req/min/IP 
{ "currentPassword": "...", "newPassword": "min 8 chars" }
POST /auth/forgot-password PUBLIC 5 req/min/IP

Password reset is code-based, not link-based: a 6-digit numeric code is emailed. Response is always identical regardless of whether the email is registered.

Request 
{ "email": "person@example.com" }
Response 
{ "expiresInSeconds": 299 }
POST /auth/reset-password PUBLIC 5 req/min/IP

The code is the credential.

{
  "email": "person@example.com",
  "code": "482913",
  "newPassword": "min 8 chars"
}
On success, every existing session on the account is revoked — whoever had the old password is signed out everywhere, not just on the device doing the reset.
  • 400 Code is invalid or expired.
  • 409 Code was already used.
POST /auth/reset-password/resend PUBLIC 5 req/min/IP

Same body/behavior as forgot-password (delegates to it directly) — the "Resend code" button on the enter-code screen.

Two-factor authentication (TOTP)

Authenticator-app based (RFC 6238, ±30s clock-drift tolerance), plus 8 single-use backup/recovery codes. SMS and email-OTP are not implemented as 2FA methods yet — this is TOTP-only today.

POST /auth/2fa/setup 🔒 AUTH

No body. Generates a secret (or regenerates it, if setup was started but never confirmed).

{ "secret": "BASE32SECRET...", "otpauthUri": "otpauth://totp/NDY%20HUB:..." }

Render otpauthUri as a QR code for an authenticator app, or show secret for manual entry.

POST /auth/2fa/enable 🔒 AUTH 
{ "code": "123456" }
Returns the 8 backup codes exactly once — only their hashes are ever stored, so this is the user's only chance to save them: { "backupCodes": ["ABCD-1234", "..."] }
POST /auth/2fa/disable 🔒 AUTH 
{ "currentPassword": "...", "code": "123456-or-a-backup-code" }

Requires both the current password and a valid code — deliberate friction for a security-downgrading action. Deletes the secret and all backup codes; re-enabling later starts fresh.

POST /auth/2fa/verify PUBLIC 5 req/min/IP

Step 2 of a 2FA login, called after login() returned requires2fa.

{ "challengeToken": "from-the-login-response", "code": "123456-or-backup-code" }

Returns a full session. Challenge tokens expire after 5 minutes and are single-use. Using a backup code logs a distinct RECOVERY_CODE_USED security event (see Sessions & security).

Passkeys (WebAuthn / FIDO2)

Real @simplewebauthn implementation — Face ID (iOS/Safari), fingerprint (Android/Chrome), Windows Hello, or a hardware security key all work through this.

No biometric data is ever sent to or stored by NDY HUB. The device/OS verifies the biometric locally and only sends back a cryptographic signature.

A successful passkey login issues a session directly without also requiring TOTP, even on a 2FA-enabled account — a passkey already clears a higher bar (phishing-resistant public-key crypto plus on-device user verification) than a password does.

GET /auth/passkeys 🔒 AUTH 
[
  { "id": "...", "deviceLabel": "iPhone", "createdAt": "...", "lastUsedAt": "..." }
]
DELETE /auth/passkeys/:id 🔒 AUTH

Removes a passkey. 404 if it doesn't exist or belongs to another user.

POST /auth/passkeys/register/options 🔒 AUTH

No body. Returns WebAuthn registration options plus a challengeId — pass both straight into navigator.credentials.create() (or @simplewebauthn/browser's startRegistration()).

POST /auth/passkeys/register/verify 🔒 AUTH 
{
  "challengeId": "from-the-options-call",
  "response": { "...the browser's PublicKeyCredential, as JSON" },
  "deviceLabel": "optional, e.g. 'MacBook Touch ID'"
}
POST /auth/passkeys/login/options PUBLIC

No body — usernameless / discoverable login. Returns authentication options + challengeId.

POST /auth/passkeys/login/verify PUBLIC 5 req/min/IP 
{ "challengeId": "...", "response": { "...the browser's assertion" } }

Returns a full session. Same generic failure message whether the credential was unrecognized or cryptographic verification failed — no oracle for which one it was.

Social login (Google / Apple)

GET /auth/oauth/providers PUBLIC 
{ "google": true, "apple": false }

Lets the frontend decide whether to render each button at all, based on whether credentials are actually configured server-side.

GET /auth/oauth/:provider/start?next=/dashboard PUBLIC

:provider is google or apple. A real browser navigation (302 redirect to the provider's consent screen) — link to it with an <a href>, don't fetch it.

GET /auth/oauth/google/callback
POST /auth/oauth/apple/callback

The provider redirects/posts here. Google uses a GET redirect; Apple posts (response_mode=form_post, required whenever name/email scopes are requested). Both end in a 302 redirect back to the web app with a one-time exchange code in the URL — the actual tokens never appear in a URL.

POST /auth/oauth/exchange PUBLIC 5 req/min/IP 
{ "code": "the-one-time-code-from-the-callback-redirect" }

Returns a full session.

POST /auth/oauth/:provider/connect 🔒 AUTH

Same as start, but for linking a social account to an already-logged-in user ("Settings → Connect Google"). Returns { "url": "..." } as JSON instead of redirecting — the frontend navigates the browser there itself.

GET /auth/me 🔒 AUTH 
{
  "id": "uuid",
  "ndyId": "NDY-4F82XK",
  "email": "person@example.com",
  "fullName": "Jane Doe",
  "profilePhotoUrl": "https://...",
  "verificationLevel": "LEVEL_1",
  "ndyappsConnected": false,
  "twoFactorEnabled": false,
  "role": "USER",
  "createdAt": "...",
  "bio": "...", "country": "...", "website": "...",
  "linkedinUrl": "...", "instagramUrl": "...", "xUrl": "...",
  "businessName": "...", "businessRole": "...", "phone": "...",
  "bioIsPublic": true, "countryIsPublic": true, "websiteIsPublic": true,
  "socialsIsPublic": true, "businessIsPublic": true, "phoneIsPublic": true,
  "passportComplete": true,
  "isVerified": false
}

verificationLevel runs LEVEL_0 (unverified) through LEVEL_3; confirming email moves LEVEL_0 → LEVEL_1. passportComplete reflects whether the required Passport fields (full name, country, photo) are filled in — the dashboard routes anyone false here to a completion screen first.

PATCH /auth/me 🔒 AUTH

Same body shape as the optional fields in Registration (fullName, bio, country, website, linkedinUrl, instagramUrl, xUrl, businessName, businessRole, phone, and the matching *IsPublic booleans, plus profilePhotoUrl as a direct URL string). Returns the same shape as GET /auth/me.

POST /auth/me/photo 🔒 AUTH

multipart/form-data, field name photo. JPEG/PNG/WebP only, max 5MB — SVG is deliberately rejected since it can carry inline <script>.

{ "profilePhotoUrl": "https://..." }

Sessions & security

GET /security/sessions 🔒 AUTH

Every active (non-revoked, non-expired) session/device currently signed in.

[
  {
    "id": "uuid", "userAgent": "Mozilla/5.0...", "ip": "203.0.113.4",
    "createdAt": "...", "expiresAt": "...", "isCurrent": true
  }
]
DELETE /security/sessions/:id 🔒 AUTH

Revokes one session. 404 if it isn't active or doesn't belong to the caller.

POST /security/sessions/revoke-all 🔒 AUTH

Logs out every device, including the one making the call. Its access token stays valid until natural expiry (max 15 min — it's a stateless JWT, nothing to revoke there) but the refresh token behind it is dead.

{ "revokedCount": 3 }
GET /security/events 🔒 AUTH

The account's security activity timeline — up to the 50 most recent events, newest first.

[
  { "id": "uuid", "type": "LOGIN_SUCCESS", "ip": "203.0.113.4", "userAgent": "...", "createdAt": "..." }
]

type is one of:

LOGIN_SUCCESSNEW_DEVICEPASSWORD_CHANGEDPASSKEY_ADDEDPASSKEY_REMOVEDTOTP_ENABLEDTOTP_DISABLEDRECOVERY_CODE_USEDEMAIL_CHANGEDOAUTH_APP_CONNECTEDOAUTH_APP_REVOKED

NEW_DEVICE fires alongside LOGIN_SUCCESS the first time a given User-Agent string signs in on that account — a first-seen check against prior sessions, not full device fingerprinting. This log is distinct from the admin-only audit log: every row here is something the account owner did themselves, or that happened to their own account.

Connected accounts (social)

GET /auth/connected-accounts 🔒 AUTH

Google/Apple accounts linked for sign-in — distinct from OAuth client grants below (this is "which social providers can I log in with," not "which third-party apps can access my data").

DELETE /auth/connected-accounts/:id 🔒 AUTH

Unlinks a social provider. Rejected with 409 if this would leave the account with no way to sign in at all — no password, no other linked social provider, and no passkey.

OAuth2 / OIDC provider — connecting your app to NDY HUB

NDY HUB is a standards-compliant OpenID Connect provider. This is the mechanism NDJOYIT, NDYAPPS, and every future NDY product use to authenticate against the same identity without maintaining their own password store. Authorization Code Flow with PKCE — S256 only, plain is rejected.

Discovery: GET /.well-known/openid-configuration and GET /.well-known/jwks.json — standard OIDC discovery documents. Any off-the-shelf OIDC client library can integrate against these without NDY HUB-specific code.

Supported scopes:

ScopeGrants
openidConfirm who you are (required on every connection)
profileName and NDY ID
emailEmail address
membershipCurrent membership tier and status
cryndyAvailable CRYNDY balance

The full flow:

  1. Your app redirects the user's browser to GET /oauth/authorize with your client_id, redirect_uri, response_type=code, requested scope, a random state, and a PKCE code_challenge (S256).
  2. NDY HUB redirects to its own /oauth/consent screen. If the user is already logged into NDY HUB and has previously approved everything you're asking for, they may skip straight through — that's the "one login, not one login per visit" part of SSO.
  3. On approval, NDY HUB redirects back to your redirect_uri with a one-time code and your original state.
  4. Your backend (never the browser) exchanges that code at POST /oauth/token using your client_id/client_secret and the PKCE code_verifier.
  5. NDY HUB returns a standard OIDC token set: access_token, id_token, refresh_token, expires_in.
  6. Call GET /oauth/userinfo with the access token to fetch the claims your granted scope allows.
GET /oauth/authorize 
?client_id=...&redirect_uri=...&response_type=code
&scope=openid+profile&state=...
&code_challenge=...&code_challenge_method=S256

Browser redirect entry point. Never redirects back to your app on a bad client_id/redirect_uri (that's an open-redirect phishing vector) — renders a plain error instead.

GET /oauth/authorize/status 🔒 AUTH

Called by NDY HUB's own consent page — you won't normally call this from your app.

{
  "client": { "name": "NDYAPPS", "...": "..." },
  "scopeDescriptions": [{ "scope": "profile", "description": "Your name and NDY ID" }],
  "alreadyGranted": false
}
POST /oauth/token SERVER-TO-SERVER

Your backend calls this directly with client_id/client_secret — the browser never sees it.

Authorization code grant 
{
  "grant_type": "authorization_code",
  "code": "...",
  "redirect_uri": "...",
  "code_verifier": "...",
  "client_id": "...",
  "client_secret": "..."
}
Refresh token grant 
{
  "grant_type": "refresh_token",
  "refresh_token": "...",
  "client_id": "...",
  "client_secret": "..."
}

Standard OIDC token response shape: access_token, id_token, refresh_token, expires_in, token_type.

GET /oauth/userinfo 🔒 OAUTH TOKEN

Bearer-authenticated with the OAuth access token from the token endpoint (not an NDY HUB session token). Returns claims matching the granted scope.

GET /oauth/grants 🔒 AUTH
DELETE /oauth/grants/:id 🔒 AUTH

The user-facing "which apps are connected to my account" list and revoke action — the same data shown on NDY HUB's /security dashboard page. Revoking also kills every refresh token that client holds for the user, not just the grant record.

QR / cross-device login

Used by NDYAPPS-style flows where a desktop browser shows a QR code and a phone (already logged in) approves it. Requests expire after 90 seconds.

MethodPathWhat it does
POST/auth/login-requestDesktop creates a pending request, gets a token back to render as a QR code / poll.
GET/auth/login-request/:tokenPoll for status (PENDING / APPROVED / DENIED / EXPIRED). Prefer the login-request:status WebSocket event over polling.
POST 🔒/auth/login-request/:token/approvePhone approves — requires a valid NDY HUB session.
POST 🔒/auth/login-request/:token/denyPhone denies.
POST/auth/login-request/:token/exchangeDesktop, once it sees APPROVED, trades the token for a real session.

Rate limits

Every credential-guessing-relevant endpoint — register, login, 2FA verify, passkey login verify, OAuth exchange, forgot-password, reset-password and its resend, change-password, both email-verification resend endpoints — is limited to 5 requests/minute/IP, tighter than the app-wide default of 100/minute. Exceeding it returns 429 Too Many Requests.

Error shape

Standard NestJS / class-validator shape:

{
  "statusCode": 400,
  "message": "Incorrect email or password.",
  "error": "Bad Request"
}

message can be a string or an array of strings (validation errors, one per failing field). Error messages are deliberately generic wherever a specific one could leak account existence — login, password reset, and email verification resend all use the same message regardless of whether the target account exists.
